# ADR 0002：目录留在运行时，模型只接收摘要

## Context

Planner 每执行一步都会收到历史 observations。若把12条阈值和16条配置的完整 JSON
反复发送，Token 会随步骤增长，且模型可能直接在目录中猜选配置，弱化确定性优化器边界。

## Decision

- 完整目录仅保存在 LangGraph runtime context；
- Planner observation 只包含目录名、行数和有限枚举摘要；
- 最终优化结果仍完整写入轨迹；
- 每次模型调用保存脱敏 request ID、attempt、延迟和 usage，不保存 API Key；
- usage 或带日期价格元数据不完整时不估算成本。

## Alternatives

- 每步发送完整目录：实现简单但浪费 Token，并扩大模型自行计算空间；拒绝。
- 完全不告诉模型目录已加载：会增加重复调用；拒绝。
- 只保存汇总 usage：无法定位429、重试或单次延迟异常；拒绝。

## Evidence

测试验证 Planner 看到的目录 observation 不包含配置 ID；完整目录仍可供优化器使用；
逐调用遥测是副本且不含测试密钥；当前全量测试61项通过。

## Consequences

模型能够判断目录是否加载，但不能检查每一行。领域完整性由运行时验证器和确定性优化器
承担，这是刻意的职责分离。若未来新增需要模型解释候选差异的任务，应新增专门的有界摘要
工具，而不是重新暴露整个目录。

## Adversarial review

可能质疑“模型看不到候选就不算规划”。本项目的模型职责是解析约束和选择工具，数值搜索
由确定性优化器完成；让模型读取全部候选并自行比较反而会降低可复核性。
